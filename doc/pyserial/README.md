# Python backends: `pytest` and `pyserial`

Two new backends that run pipeline modules written in Python, concurrently,
inside the existing TBB schedule:

- **`pytest`** — forked from `fwtest`. The framework work happens here: several
  products of one type per event, a configuration language, and Python modules
  through a free-threaded interpreter with nanobind bindings generated by
  ROOT/cling.
- **`pyserial`** — forked from `serial`. The same framework changes applied to
  the real pixel reconstruction, with the vertex reconstruction rewritten in
  Python so the two can be measured against each other.

This document records the decisions taken while building them: what the
alternatives were, which was chosen, and why. It is written for a reader who
wants to disagree with a choice and needs to know what it was weighed against.

---

## D1. Where the framework work happens

**Alternatives.** (a) Modify `fwtest` in place and have `pytest` be only the
Python modules. (b) Fork `fwtest` into `pytest` and change the fork.

**Chosen: (b).** Every backend in this repository already carries its own copy
of `Framework/`, `bin/` and `DataFormats/`; that duplication is the repository's
existing design, not an accident. Changing `fwtest` would alter the behaviour of
a backend other people use as a reference, and the product-registry change in
particular is not backward compatible. Forking keeps `fwtest` available as the
control.

**Consequence.** Framework fixes do not propagate between backends. The changes
made in `pytest` are re-applied by hand to `pyserial` (task 9), and that
re-application is a place bugs can hide; the two `Framework/` trees should be
diffed whenever one changes.

---

## D2. Naming

`pytest` collides with the Python testing framework of the same name. It is the
name asked for, and backend names in this repository are directory names rather
than importable modules, so nothing actually imports it. Worth knowing if a
`python -m pytest` ever runs from the repository root.

---

## D3. Several products of the same type in one event

**The problem.** `fwtest`'s `ProductRegistry` keys products on `std::type_index`
alone, and `produces<T>()` throws if that type is already registered. The
comparison workflow needs two `std::vector<float>` products in one event — one
squared in C++, one in Python — so the type alone cannot identify a product.

**Alternatives.**

- **(a) Distinct C++ types per producer.** `SquaredCxx` and `SquaredPy` as
  separate structs. Requires no framework change, and is what the rest of
  pixeltrack-standalone does. But it makes the *type system* carry which
  implementation produced a value, so a consumer cannot be written once and
  pointed at either; the comparison module would need two tokens of two types,
  and a third implementation would mean a third type.
- **(b) Key products on (type, label).** The label is the producing module's
  configuration label. This is what `demo::Event` does with producer names, and
  a cut-down version of CMSSW's `(type, label, instance, process)`.

**Chosen: (b).** It is the model both the nanobind demo and CMSSW already use,
it keeps one C++ type per *concept* rather than per implementation, and it is
what makes a Python module a drop-in replacement for a C++ one — the whole point
of `pyserial`. Cost is a change to a file every backend copies, which is why the
`Framework/` trees now differ between `pytest`/`pyserial` and the rest.

**Consequence.** `consumes<T>()` is now ambiguous when several modules produce
`T`. Rather than pick one, the unlabelled overload throws and names the count;
a module that wants a particular one calls `consumes<T>(label)`. The unlabelled
form is kept because most products *are* unique, and keeping it means the ported
`serial` plugins compile unchanged.

## D4. Configuration language

**Chosen:** boost `property_tree` INI, the same shape as the nanobind demo:
`[options] modules = a, b, c` for the schedule, one `[label]` section per module
with `@type` naming the plugin and the rest being that module's parameters.

**Why property_tree rather than a hand-written parser.** A ~80-line parser would
avoid a dependency, and the system boost here (1.75.0) is older than this
repository's minimum (1.78.0), so `BOOST` means building an external. But
`serial` — which `pyserial` forks — already lists `BOOST` in its
`EXTERNAL_DEPENDS`, so the external is built for the work that actually matters
either way. Given that, matching the demo is worth more than saving a
dependency that is already paid for.

**Kept from the demo:** an unknown key in `[options]` is an error, and a
scheduled label with no section is an error. Both were silent no-ops in the demo
once and produced a measurement that quietly meant nothing.

## D5. Configuration versus the command line

**Alternatives.** (a) Move everything into the configuration, including thread
and stream counts. (b) Keep run-time options on the command line and let the
configuration supply only defaults.

**Chosen: (b), command line wins.** `run-scan.py`, `run-many.py` and the
`test_*` make targets all drive `--numberOfThreads` / `--numberOfStreams` /
`--maxEvents`. Phase 2 is a measurement exercise that depends on that tooling,
so taking those switches away from it would cost more than the tidiness is
worth. `[options]` sets defaults; an explicit switch overrides them.

## D6. How a module receives its configuration

**The problem.** `WorkerT<T>` constructs `T(ProductRegistry&)`. Passing
configuration means changing that signature, and with it every plugin in the
backend — about ten of them in `serial`.

**First tried:** two constrained constructors on `WorkerT`, selected with a
C++20 `requires` clause, so that a plugin could be written either way and only
the modules that read a parameter had to be touched.

**Chosen:** one signature, which every module uses:

    Module(edm::ModuleConfig const& config, edm::ProductRegistry& reg);

**Why the change.** Accepting both spellings saved a one-line edit in seven
plugins and cost a concept, two `requires` clauses, and a rule a reader has to
know. Worse, the fallback is silent: a module meant to take parameters but
declared with the old signature still compiles and still runs, ignoring its
configuration section. With one signature that is a compiler error. The
modules that take no parameters ignore the argument, which is the ordinary
cost of a uniform interface.

## D7. Where Python and ROOT come from

**Python.** A free-threaded `python3.14t` on the system is used when there is
one; otherwise `uv` installs CPython under `external/python`. Either way the
thing embedded is a venv under `external/venv`, so the two paths differ only in
where the interpreter came from and everything downstream is identical.

Free-threading is checked, not assumed: the build refuses to generate
`python-config.mk` from an interpreter whose GIL is enabled, and the job prints
the GIL state at startup next to the stream count. With the GIL on, the Python
modules of every stream serialise, and a throughput compared against an all-C++
run measures that rather than anything about Python. That failure is silent by
nature, so it is made loud in two places.

**ROOT.** A system installation is used when `rootcling` and `root` are on the
PATH. ROOT is a build-time dependency only — `rootcling` and one macro, with
nothing linking against it — so downloading a ~500 MB binary distribution to
obtain a tool that already exists is not worth it. It was verified here that
the system rootcling (6.40.02, built for C++17) reflects C++20 product headers
and that the dictionary compiled with g++-14 loads back into ROOT. If a system
ROOT is missing the build fails with a clear message rather than silently
skipping the reflected bindings.

## D8. Where nanobind and the generated bindings live

**The problem.** Two things have to be placed, and they pull in opposite
directions. nanobind's amalgamation must be compiled into exactly one object:
two copies would each keep their own type registry, and casts would stop
working across the boundary. The generated bindings, on the other hand, name
every product type, so whatever holds them has to link against the product
libraries — and `libFramework.so` cannot, since `CUDACore` depends on
`Framework` rather than the other way round.

**Alternatives.** (a) Compile the amalgamation into every object that needs it —
rejected, that is the two-registries failure. (b) Keep all nanobind usage inside
`libFramework.so` and give everything else a nanobind-free interface — which
works only as long as nothing above `Framework` needs nanobind, and the
bindings do. (c) Build nanobind as a shared library. Its CMake support does
that, but so do two of its own switches, with no second build system involved:
`NB_SHARED` turns the core API from hidden symbols into exported ones, and
`NB_BUILD` marks the one object that defines them.

**Chosen: (c), as three shared objects.** `libnanobind.so` is the only place
the amalgamation is compiled. `edm_core.so` holds the generated bindings: a
Python extension in the library directory, linked against the product libraries
and sitting above them, which the interpreter imports by name — `PythonRuntime`
puts that directory on `sys.path` first. `libFramework.so` uses nanobind but
owns no module of its own, and that takes one extra call: each shared object
keeps its own pointer to nanobind's backend state, filled when *that* object
initialises a module, so Framework's would stay null and the first import from
`PythonModuleRunner` segfaults with no output at all.
`nanobind::register_module()` is the way in — it joins the domain `edm_core`
created rather than making a second one, so there is still exactly one type
registry in the process.

`PythonModuleRunner` stays a pimpl whose header mentions no nanobind, and
`plugin-Demo/PythonProducer.cc` is ordinary C++. Nothing requires that here —
with the core API exported, a plugin could use nanobind directly — but it keeps
a future Python-backed module in any plugin costing nothing extra.

## D9. Every binding is generated — and why the first version of this was wrong

**This decision was originally recorded the other way round, and it was wrong.**
The first version said reflection could not know that an array of scalars should
become a zero-copy numpy view, because "nothing in a C++ declaration says so",
and so those adapters were hand-written.

That is false. The dictionary carries the element type *and* the extent:

    field zv: float, dim=1, ext=1024, offset=65536, public

which is exactly what a numpy view needs. The hand-written adapters were not
compensating for missing information; they were duplicating information the
dictionary already had, in a place where it could fall out of step.

**Now:** `tools/generate_bindings.C` is given the backend's product types and
reflects the transitive closure of everything reachable from them, whether or
not a Python module uses it. Per class it emits

| declaration | binding |
|---|---|
| scalar member | `def_rw` |
| `T member[N]` | `def_prop_ro` giving a zero-copy numpy view of N elements |
| class member | `def_prop_ro` by reference; that class is bound too |
| `static const` scalar | `def_prop_ro_static` |
| method | `def`, through a lambda |
| `std::vector<scalar>` | `size()`, `resize(n)`, `.data` as a view |

It also emits the `Event.get` / `Event.emplace` dispatch, so there is no table
anywhere kept in step by hand.

**Three things the implementation turns on.**

- **Methods are emitted as lambdas, not member-function pointers.** Several
  return `auto` — `HeterogeneousSoA::get()` does — which cannot be spelled in
  the cast a member pointer needs, but a lambda lets the compiler deduce it. It
  also collapses const/non-const overload pairs, where taking an address would
  be ambiguous.
- **A wrapper says what it owns through its constructor.** `HeterogeneousSoA`
  keeps its `unique_ptr` private, so the payload type appears nowhere in the
  public members; the constructor taking `unique_ptr<X>&&` is the only place the
  dictionary spells X out. That is what the generator follows, both to reflect X
  and to know how to construct the product for `Event.emplace`.
- **A format has to make public what it wants bound.** `eigenSoA`'s storage was
  private, reachable only through a `data()` that returns a bare pointer with no
  extent. It is now public, with a comment saying why: for the bindings to be
  generated, the storage is part of the interface.

  This is the one place where a data format was changed to suit the generator,
  and it should be read as a property of *this* format, not as a general
  requirement. `eigenSoA` is ancient. The SoA layouts that replaced it in CMSSW
  expose each column as a `std::span`, which carries its own extent and is
  public by construction; a `std::span` rule in the generator would bind those
  with no change to the format at all. The change here buys back by hand what
  the modern layouts give for free, so it should not be carried forward as
  precedent.

**Result for pyserial:** 10 classes, 14 fields, 13 zero-copy views, 24 methods,
all generated. The Python vertex finder reads `tracks.pt.data_`,
`tracks.detIndices.off`, and slices component 4 of `tracks.stateAtBS.state`,
every one of them a generated view over the C++ product's own memory.
Throughput is unchanged from the hand-written version, within run-to-run
scatter.

**What is still hand-written, and why it is not a product binding.**
`Framework/Bindings.cc` binds `edm::Event`, `edm::ProductRegistry` and the two
token types. Those are the mechanism by which products are reached, not things
stored in an Event, and they have no dictionary. No product type is named
anywhere under `Framework/`, which is what lets that directory be byte-identical
between the two backends.

## D10. Two bugs inherited from fwtest

Worth recording because both were silent.

**`Wrapper<T>` brace-initialises its payload.** `event.emplace(token, n, 0.0f)`
on a `std::vector<float>` therefore built a *two-element* vector — `{n, 0.0f}`
as an `initializer_list` — rather than `n` elements, and moving one vector into
another did not compile at all. A tag-selected parenthesised constructor is used
for the cases that need it; the brace-initialising one is kept, because an
aggregate product needs it.

**`Event` was copyable in declaration only.** It owns its products through
`unique_ptr`, so the implicit copy constructor existed but could never compile.
Nothing copied an Event, so nothing noticed until nanobind tried to instantiate
`wrap_copy<Event>`. Now deleted, which is both what was always true and what
lets the type be bound.

## D12. Every binding the generator emits, covered

D9 leaves the generator as the thing that has to be right: no binding is
written by hand, so a mistake in `tools/generate_bindings.C` is a mistake in
every product at once. What this backend had to check it with was a
`std::vector<float>` and a four-field aggregate — a scalar member and a
container, which is a small corner of what the generator emits.

`bindings.ini` covers the rest. Two products carry the shapes a real format
has, with none of the content. `pytest::Calibration` is conditions, read both
one channel at a time — a method taking an argument, a class member, a
fixed-size array, a static constant — and as columns. `pytest::Samples` is a
structure of arrays with `std::span` columns, a view handed out by reference
and a method with a side effect, built by a constructor that wires it to the
conditions and to a column.

`CalibrateCxx` and `python/calibrate.py` build the same product from the same
input and the same conditions; `SamplesCompare` compares them column by column;
`python/calibrate_check.py` reads both back, which is the other half, since
calibrate.py only writes. The arithmetic is one subtraction and one
multiplication, never a multiply-add that `-march=native` could contract into
an FMA, so numpy and C++ agree bit for bit and the tolerance is zero.

| what the generator emits | where it is covered |
|---|---|
| `def_rw` scalar member | `Channel::index`, `Channel::enabled`, `View::filled` |
| `def_prop_ro` array member | `Channel::weights` |
| `def_prop_ro` class member | `Channel::gain` |
| `def_prop_ro_static` | `Calibration.kChannels`, `Samples.kMaxSamples` |
| method, no arguments | `Gain::slope()`, `Samples::size()` |
| method, with arguments | `Calibration::channel(i)` |
| method returning a reference | `Samples::view()`, `Calibration::view()` |
| method with a side effect | `Samples::applyCalibration()` |
| nested class, name made unique | `pytest__Samples__View`, `pytest__Calibration__View` |
| `std::span` column as a numpy view | `valueSpan`, `scaledSpan`, `channelSpan`, and the calibration's three |
| `registry.consumes(type, label)` | `calibrate_check.py` |
| `registry.consumes(type, "")` | `calibrate.py` |
| `event.get(token)`, class product | `calibrate_check.py` |
| `event.get(token)`, scalar product | the sample count, in `calibrate_check.py` |
| `event.allocate(token)` | `square.py` |
| `event.allocate(token, ...)`, wiring the product | `allocate(output, n, calibration, channels)` |
| `event.put(token, value)` | the count (a scalar) and the summary (a class) |
| `event.emplace(token, ...)` | `emplace_demo.py` |
| `eventSetup.get(type)`, class product | `pytest::Calibration` |
| `eventSetup.get(type)`, scalar product | the `int` of `IntESProducer`, in `square.py` |
| allocate of a scalar, put of a non-copyable | both error paths, asserted in `calibrate.py` |

Every row fails the job rather than printing something to be read: the two
implementations disagree, or a check in the Python module raises.

**Why a view has to come back as a reference.** Binding a method as
`[](X& o) { return o.method(); }` deduces the return type *by value*, so a
method returning a reference is bound to a copy. Reading through the copy gives
the right answer, which is what makes it dangerous — the columns are pointers
and still land in the right memory, so only a write to the view *itself* shows
the difference. `samples.view()` followed by `view.filled = n` is that write:
the value goes into a temporary, the product never sees it, and SamplesCompare
says so on the first event. The lambdas return `decltype(auto)` for this
reason.

The configurations are the tests: `make test_pytest_cpu` runs all four of them.
That target used to run `./pytest --maxEvents 2` with no configuration at all,
which has not been able to do anything since D4 made the schedule come from a
file.

# Part 2: pyserial

## D13. Which module to rewrite in Python, and why that one

`src/serial`'s path is

    BeamSpotToPOD -> SiPixelRawToClusterCUDA -> SiPixelRecHitCUDA
                  -> CAHitNtupletCUDA -> PixelVertexProducerCUDA

**Chosen: the vertex finder.** It is last, so only validation sits downstream;
its payloads are small (~10^2-10^3 tracks in, ~10^1-10^2 vertices out) so the
binding surface stays small enough to hand-write while the shape of the problem
is still being learnt; and its algorithm is genuinely non-trivial — density
clustering, weighted fits, two-means splitting, sorting — so what is measured is
real per-event work rather than call overhead.

**A scalar product crosses by value.** `pytest` inherits an EventSetup from
`fwtest`: `IntESProducer` puts a bare `int` there and `TestProducer` reads it.
Nothing on the Python side had ever touched it, and it could not have: the
generator is built on `TClass`, and a fundamental type has none --

    $ rootcling ... '#pragma link C++ class int+;'
    Warning: Unused class rule: int

The fix is not to change the data format but to notice that scalars were
already crossing by value everywhere else. Every `def_rw` on an `int` or a
`float` member of a product uses nanobind's own caster and involves no
dictionary at all; only a product that *is* a scalar fell through, and only in
the dispatch. It now emits `nb::cast(eventSetup.get<int>())` by value, and the
same for the Event; the `Makefile` keeps scalars out of the LinkDef, since
rootcling has nothing to generate for them. `square.py` reads the `int` every
event, which is what exercises the path.

This looked like an asymmetry -- a class product is filled in place, a scalar
arrives as a value -- and the first version papered over it by calling both
`emplace`. Naming the two operations for what they actually do removes it:

| | | returns |
|---|---|---|
| `event.allocate(token)` | constructs the product in the Event, nothing set | a reference to fill |
| `event.put(token, value)` | copies a product you already have | nothing |
| `event.emplace(token, *values)` | builds the product from Python values, moves it in | nothing |

`allocate` is what every Python module here uses: it is the zero-copy path, and
the reference it hands back is the product's own storage. `put` is for what has
nothing to fill -- a scalar -- and for any other product that can be copied,
which is a real operation with a real cost, named so that the cost is visible.
A product that can be neither says so at run time: the SoA wrappers hold a
`unique_ptr` and are move-only, so `put` on one reports that rather than
failing to compile the generated file.

`emplace` is the one that *constructs*, which is why `put(token, [1.0])` does
not work and `emplace(token, [1.0])` does: `put` copies a product that already
exists, and a Python list is not one. Making the list work in `put` would mean
including nanobind's `std::vector` type caster, which would then shadow the
class binding for `std::vector<float>` and copy on every crossing -- losing the
zero-copy view that is the reason it is bound as a class at all.

What `emplace` can build is decided per product by the generator, from the
dictionary, and nothing else is guessed at:

| product shape | arguments |
|---|---|
| a scalar | one value |
| `std::vector<T>` of scalars | one sequence |
| an aggregate whose members are all scalars | one value per member, in declaration order |
| anything else | an error naming `allocate` |

Binding the dictionary's own constructors was tried first and abandoned: ROOT
reports `std::vector<float>`'s as taking a
`vector<ROOT::Internal::RPageSource::RActivePhysicalColumns::RColumnInfo>::size_type`
and a defaulted allocator, so the signatures would have to be parsed and
repaired before they could be bound. Building from the values is both simpler
and closer to what a module wants to say. The aggregate case carries a
`static_assert(std::is_aggregate_v<T>)` into the generated file, so a product
that stops being an aggregate breaks the build rather than the results.

Neither returns the value put in. Returning it would read as a reference to the
product and cannot be one -- a Python `int` is immutable, so
`v = event.put(tok, 1); v += 1` would leave the product at 1 while looking as
though it had changed it.

**Could a scalar be a reference?** Yes -- not as a Python scalar, which is
immutable, but as a bound object wrapping the `int*`, with the numeric protocol
forwarded to it. It was measured before being rejected. A read through a
nanobind-bound attribute costs **35 ns** here and a write **31 ns**, against
~16 ns of bare loop overhead for a plain Python int; so every *use* of a
wrapped scalar would pay ~35 ns where a value pays nothing after the one cast
at the boundary. The complexity is worse than the cost: to behave like an
integer rather than merely convert to one, a wrapper needs the whole numeric
protocol -- some twenty-five dunders plus their reflected and in-place forms --
and anything short of that is a trap, where `x + 1` works and `math.sqrt(x)` or
a numpy call does not. For a payload of one scalar, `put` says what is
happening and costs less.

**What this does not measure.** A module with large payloads —
`SiPixelRawToClusterCUDA`, with ~10^4-10^5 digis — would test the *boundary*
rather than the compute: view construction cost and memory traffic. That is a
different experiment and the numbers here say nothing about it.

## D14. How faithful the port is, and how that is checked

The Python module runs the same sequence as
`gpuVertexFinder::Producer::make()` with the same constants, and reads and
writes the same SoAs in place.

Two of the C++ loops are order-dependent — "find closest above me" keeps a
running minimum and overwrites its answer, and `splitVertices` is a per-vertex
two-means iteration — so they are written as loops in Python too rather than
vectorised into something that would break ties differently. Everything else is
numpy.

**Checked, not asserted.** `plugin-Python/VertexCompare.cc` consumes *two*
`ZVertexHeterogeneous` products, one from each implementation, and compares
them. That module is only expressible because products are keyed by
(type, label) — under fwtest's type-only key the second producer would have
thrown. Over 200 events the two agree exactly: same vertex count, and
`worst |dz| = 0`. The stock `CountValidator` also passes with the Python
vertexer in the path.

**One bug this caught.** The first version sorted tracks by their z *bin index*
and then binary-searched that array by z. Within a bin the z values are in no
order, so the neighbour windows were wrong, and Python found up to 8 vertices
too many per event. Nothing in the throughput would have shown this; only
comparing against the C++ product did.

## D17. The two Framework trees are identical

`diff -r src/pytest/Framework src/pyserial/Framework` is empty. That is checked
rather than intended: it is the property that keeps a framework fix from having
to be re-applied by hand to the other backend, and it only holds because
everything product-specific was moved out —

- product class bindings, the `get`/`emplace` dispatch and the name →
  `std::type_index` table are generated into `$(OBJ_DIR)/<backend>/generated/`,
  not written in `Framework/`, and compiled into `edm_core.so` rather than into
  `libFramework.so`, which is what keeps the product types out of it (D8);
- `DataFormats/Products.h` is the header rootcling parses, and holds only
  declarations and includes;
- the reflected header, the product list and the include paths are three
  variables in each backend's `Makefile`.

Adding a product to a backend is one word in `REFLECT_PRODUCTS` in its
`Makefile`, plus whatever declares the type; nothing under `Framework/`
changes, and no binding is written.

## D19. The product list is written once

**Was:** `EDM_PAYLOAD_TYPES` in `DataFormats/Products.h` listed the payload
types, an X-macro expanded twice — into `PayloadName<T>` specialisations and
into the name → `type_index` table in `PayloadTypes.cc` — and `REFLECT_PRODUCTS`
in the `Makefile` listed the same types again for rootcling and the generator.

**Now:** only `REFLECT_PRODUCTS`. The generator emits `payloadTypeNames()` and
`payloadTypeIndex()` alongside the dispatch it already generated from that list;
`Framework/PayloadTypes.h` keeps their two declarations, `PayloadTypes.cc` is
gone, and so is the macro.

**Why.** Two reasons, and the first is the one that matters.

The header and the `Makefile` had to agree and nothing checked that they did.
Adding a type to `Products.h` but not to `REFLECT_PRODUCTS` builds cleanly and
fails at run time, the first time a Python module asks for it — and only if one
does.

The X-macro also no longer earned its keep. It is the right idiom for a list
that expands into several unrelated places, and this one had two expansions;
but `PayloadName<T>` / `payloadName<T>()` turned out to have no callers at all,
written on the assumption that C++ would want to name a product type when
everything that needs a name is on the run-time path. With one expansion left,
the macro was a worse way of writing the one thing it expanded into.

**What is checked.** Asking for a type that is not a payload still names the
alternatives, now from the generated list:

    RuntimeError: unsupported payload type 'NoSuchType';
    known types are std::vector<float>, pytest::Comparison

## D18. A backend carries its own tools

`generate_bindings.C` started as `tools/generate_bindings.C` at the top of the
repository, shared by both backends. It is now `src/<backend>/tools/`, one copy
each, and each `Makefile` runs its own.

**Why.** A backend in this repository is meant to be self-contained: it carries
its own `Framework/`, its own `DataFormats/`, its own plugins. A generator that
turns *that backend's* product list into *that backend's* bindings belongs with
them. Sharing it means a change made for one backend silently rebuilds the
other, which is exactly the coupling the per-backend layout exists to avoid.
The cost is the usual one for duplication: a fix has to be applied twice, and
the two copies are byte-identical today only because nothing has needed to
differ yet.

`pyconfig.py` travels in the same directory but is not per-backend: it reports
the flags of the one interpreter every Python backend links against, into the
shared `external/python-config.mk`. Rather than privilege one backend's copy,
the top-level `Makefile` takes the first it finds:

    PYCONFIG := $(firstword $(wildcard $(SRC_DIR)/*/tools/pyconfig.py))

Moving `tools/` into the backends also exposed an inherited assumption in the
backend `Makefile`: `LIBNAMES` took *every* entry in the backend directory that
was not a plugin, so `python/`, `test.ini` and `square.ini` were already being
built into empty libraries and linked against, and `tools/` would have joined
them. A library is now a directory that holds `.cc` files, with `bindings/`
named as the one exception: `edm_core.so` is an extension module the
interpreter imports, not a library anything links against.

A second one cost more. The dictionary depended on `DataFormats/Products.h` and
not on the headers it includes, so editing a product's declaration left the
bindings stale: the build succeeded, and only a Python module found out, at run
time. Making `eigenSoA`'s storage public and rebuilding produced exactly that --
`'ScalarSoA_unsigned_char_32768' object has no attribute 'data_'` against a
dictionary generated before the change. The header list now comes from the
compiler, the way it does for every object file here.

## D20. The beam spot

`beam_spot.py` is a port of `BeamSpotToPOD`, which is one line of C++: it moves
eleven floats from the EventSetup into the Event, and computes nothing.

What it shows is the difference between crossing into Python and reading a
scalar attribute.  Attaching a thread state, building the `Event` and
`EventSetup` argument objects and calling into Python are cheap; a scalar
attribute goes through nanobind's attribute protocol on every read and write.
That is why bulk data has to cross as a view rather than as attributes: a
module that touched 10^4 hits one field at a time would spend its time on the
attribute protocol rather than on Python.

## D21. The rec hits: a big payload

`pixel_rechits.py` is a port of `gpuPixelRecHits.h`: it reads five columns of
digis and four of clusters and writes thirteen of rec hits.

| product | per event |
|---|---|
| digis in | 48,000–67,000 |
| clusters in | 12,000–21,000 |
| rec hits out | 12,000–21,000 |

That is three orders of magnitude more objects than the vertex finder sees.

**It is bit-exact.** Over 200 events and 3,045,548 hits, no hit differs in any
of the thirteen columns and the worst absolute difference is 0 — position,
error, global coordinates, cluster sizes, charge, and the packed phi. The full
chain built on the Python hits passes `CountValidator` for tracks and
vertices. That is worth stating plainly because the port had every opportunity
to drift: the CPE position is a charge-weighted correction with branches on
cluster size and edge pixels, and phi is a degree-7 polynomial approximation
of `atan2` rather than `atan2`, so the port had to be the same polynomial.

**What made it possible.** Every column crosses as a numpy view over the C++
storage — nothing is copied in either direction — which took `std::span`
accessors on three formats and a span rule in the generator. The detector
geometry is different in kind: it comes from the EventSetup and does not
change, so the module gathers 1856 modules' worth of CPE parameters into numpy
arrays once per stream, rather than re-reading 37,000 scalar attributes (D20)
on every event.

**Where D12's rule earned its keep.** The rec-hit product is constructed
around the *address* of the CPE parameters. Had `view()` or `detParams()` been
bound by value, that address would have belonged to a Python temporary: a
segmentation fault at 16 streams and nothing at all at one, because the freed
memory is not reused quickly enough to notice. `decltype(auto)` is what keeps
the reference a reference.

## D23. The clusterizer: raw bytes, and a graph

The one module whose input is not already a column.  SiPixelRawToClusterCUDA
reads the FED buffers as bytes, decodes 32-bit words into pixel coordinates
through the cabling map, calibrates each pixel with the gain conditions, groups
the pixels of each module into clusters and cuts the clusters that carry too
little charge.  The first three of those are bit fields, table lookups and
arithmetic — numpy does them over the whole event at once, the way every module
before this one did.

The clustering is different in kind, and it is the reason this module was left
until last.  The C++ kernel walks one module at a time: it bins the pixels by
column into a histogram, builds a neighbour list from the bins, iterates `min`
over that list until nothing changes — alternating with a pass that follows
every label to its root — and finally numbers the clusters by scanning the
pixels in order and counting the ones that are their own label.

Translating that is not the same as rethinking it, and this module does the
first.  The algorithm is the kernel's; what changes is that each of its steps
is a column.  The histogram is a sort by (module, column, row), one for the
whole event rather than one per module.  The neighbour list is two
`searchsorted` ranges per pixel — the rest of its own column, and all of the
next one, both within a row.  The `min` iteration is a reduction over every
neighbour pair at once.  The numbering is a cumulative sum over the pixels that
are their own label.  Nothing about which pixels end up in which cluster is
decided differently, which is what makes the products identical rather than
merely close.

Whether the kernel's algorithm is the right one to give numpy is a separate
question, and one this port deliberately does not answer here; D27 does.

**It agrees exactly.**  Over 200 events, with no difference in any of the seven
digi columns — x, y, charge, module, cluster, the packed digi and the raw
detector id — and none in the four per-module columns.
`reco-python-validate.ini` then reconstructs the whole chain from the Python
clusters and CountValidator passes, which is the check that matters: the digi,
cluster, track and vertex counts all come out of a Python chain that now starts
at the raw data.

**What it needed.**  Four conditions and one event product had to become
reachable: FEDRawDataCollection and the cabling map, the gains and the FED list
from the EventSetup.  Between them they wanted the same three things the
formats wanted in D21 — a column as a pointer and a length rather than a bare
pointer, a reference rather than a pointer to a class, and a scalar accessor
where the declaration is something reflection cannot describe (`rangeAndCols`
is an array of nested `std::pair`s).

One build-level detail came with them.  `allocate()` learned to call a
constructor that takes only a size: the digis and the clusters are sized for
the largest event the detector can produce and then filled, which is the other
half of the wiring constructor D21 added, so the rule is now "the constructor
with the most arguments, and a wiring one over a sizing one of the same
length".  Nothing else had to change for these formats — their constructors and
their destructors stay in the `.cc` files they were always in, because the
bindings are compiled into `edm_core`, which links against the product
libraries (D8).

## D24. The validation, in Python, and what a module needs at the end of a job

CountValidator is not a reconstruction module: it publishes nothing, it reads
the counts the source carries next to the raw data and checks the chain against
them, and what it reports is the whole job rather than one event.  That makes
it the first module whose state does not belong to a stream.

A C++ module says so with a `static` counter and an `endJob()`.  A Python
module now says the same thing the same way: module-level names are shared by
every stream's instance -- the script is imported once -- and `endJob()` is
called on the first stream's module only, exactly as it is for a C++ module.
The runner calls it if the object has one, so a module with nothing to do at
the end of the job simply does not define it.

The one thing that is genuinely different is the locking.  A C++ module gets
`std::atomic` counters; on a free-threaded interpreter `+=` on a module-level
integer is not atomic either, so the updates go under a `threading.Lock`.  It
is held for the counter update and nothing else -- the work of the event
happens outside it -- which is the same discipline the C++ module follows with
its one mutex around the track-difference sum.

`validation = true` in `[options]` is what puts it in the path, and it does two
things: the source starts producing the counts, and the label `countValidator`
is scheduled.  The label is what matters, not the plugin behind it, so
reco-python-validate.ini names a PythonProducer there and the same flag runs
the Python validator.

Over the same events it reports the same verdict and the same average
difference as the C++ one, to the digit.

## D25. The histograms, byte for byte

HistoValidator is the last of them: thirty-three histograms of the digis,
clusters, hits, tracks and vertices, written to a file at the end of the job.
The interesting part is that the file is a *format*, so this port either
reproduces it exactly or it is no use — and reproducing it means reproducing
SimpleAtomicHisto's binning, which has two quirks worth keeping: `nbins + 2`
bins with underflow and overflow at the ends, and a value that scales exactly
to `nbins` folded back into the last real bin rather than into the overflow.

Both are one line of numpy over a whole column at a time, and `np.bincount` is
what turns a column of bin indices into counts — the fill loop of the C++
module, which is per value, does not appear at all.  The output format is
`ostream`'s default for a float, which `%g` matches.

The two files are byte for byte identical.

The counters are the job's, as in D24, and for the same reason: a histogram is
filled by every stream.

Neither validator is on the measured path — reco.ini and reco-python.ini run no
validation, which is what keeps a throughput difference between them the
reconstruction and nothing else.

## D27. The same module twice, differing only in the algorithm

The clusterizer is the only module whose C++ is plain loops over pixels rather
than a call into somebody else's library, so it is where the way a port is
written matters most.

Writing a column where the C++ writes a loop over pixels is *translation*: the
quantities, their order and the branches are all still the C++'s, and no other
module in this backend was written any other way.  Choosing a different way to
arrive at the same labelling is not.

So there are two modules, and they differ in one method.
`python/pixel_clusters.py` is the translation of D23, findClus included: the
pixels themselves as nodes, every pair within a column and across two adjacent
columns as an edge, the minimum propagated over all of them every round with
the odd rounds following each label to its root.  `python/pixel_clusters_optimised.py`
replaces that labelling with two ideas of its own:

- a run of touching pixels within one column is one cluster by construction, so
  the labelling can take runs as its nodes.  There are only about a quarter
  fewer of them -- 1.38 pixels to a run, since a cluster is longer along the
  column than across it -- but what they remove is exactly the chains the
  minimum would otherwise walk one edge at a time;
- the rounds are wildly uneven: a few of them settle all but a few dozen runs
  of forty thousand, and a stubborn cluster drags the rest out, each round
  still reducing over every edge.  A run's label can change only if a
  neighbour's did, so each round hands the next one only the runs next to those
  that moved.

Everything else -- the FED walk, the decoding, the calibration, the module
boundaries, the charge cut, the numbering, the products -- is one copy of the
code, in `python/pixel_clusters_common.py`, so that the two differ in the
algorithm and nothing else, and so that a fix to any of it cannot reach one
module and not the other.  Neither module is written in terms of the other:
what they share is a third file, not a base class.

Both are exact against SiPixelRawToClusterCUDA.

Both modules put every module's pixels into one graph, because a loop over 1856
modules in Python would pay the interpreter 1856 times an event; batching them
is not an optimisation but the only way to write the thing in numpy at all.
That batching is also what creates the long tail the active set then removes:
the round count of one big graph is set by the worst cluster anywhere in the
event, while the C++ kernel, working one module at a time, stops as soon as
*that* module settles and never sees a tail.  So the same two ideas are worth
much less in C++ than they are here.

Both modules are configured, not switched: `reco-python.ini`,
`reco-python-validate.ini` and `reco-compare.ini` run the translation, and
`reco-optimised.ini`, `reco-optimised-validate.ini` and
`reco-optimised-compare.ini` are the same three files with the other module.
The comparison configurations check either of them against the C++ module the
same way.
